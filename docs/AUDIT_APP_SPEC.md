# สเปกสำหรับพัฒนาแอป Jonglock Audit แยก

วันที่บันทึก: 9 พฤศจิกายน 2026

สถานะ: เตรียมข้อกำหนดสำหรับพัฒนาภายหลัง ยังไม่เริ่มสร้างโปรเจกต์หรือเขียนโค้ด

แอป Audit เป็นแอปแยกสำหรับเจ้าหน้าที่ตรวจตลาด โดยใช้เทคโนโลยี API โครงสร้าง UI และการทำงานหลักของระบบออดิทในแอปผู้ค้าเดิม เพิ่มการสร้าง QR เรียกเก็บเงินจากผู้ค้าได้ทันที และรองรับตลาดที่ตั้งค่า “เก็บเงินเอง” ผ่านหน้าเก็บเงินแบบ POS ที่ไม่ต้องมีบูธหรือการจอง

## ข้อกำหนดที่ตกลงแล้ว

| หัวข้อ | ข้อกำหนด |
| --- | --- |
| เทคโนโลยี | ใช้ Tech stack เดียวกับแอปผู้ค้า รองรับ Android และ iOS |
| โลโก้และไอคอน | ใช้รูปเดิม เพิ่มแถบคาดสีแดงและข้อความ AUDIT สีขาว |
| API | ใช้ API ของระบบออดิทเดิมในแอปผู้ค้า |
| UI | ใช้โครงสร้าง UI ของระบบออดิทเดิม |
| งานหลัก | คงการทำงานเดิม เพิ่มการสร้าง QR เรียกเก็บเงินจากผู้ค้าได้ทันที |
| ตลาดเก็บเงินเอง | ไม่ต้องมีบูธ ไม่ต้องมีการจอง และใช้หน้าเก็บเงินแบบ POS |

การบันทึกสเปกครั้งนี้ไม่รวมการสร้างโปรเจกต์ใหม่ การเปลี่ยนสถาปัตยกรรม การแก้โค้ดหรือฐานข้อมูล การอัปเดต dependency และการผลิตไฟล์โลโก้หรือไอคอนใหม่

## เทคโนโลยีอ้างอิงจากแอปผู้ค้า

เวอร์ชันด้านล่างเป็นฐานอ้างอิงจากแอปเดิม ต้องตรวจเวอร์ชันจริงอีกครั้งเมื่อเริ่มพัฒนา โดยคงข้อกำหนดให้ใช้ Tech stack เดียวกัน

| ส่วน | ฐานอ้างอิง |
| --- | --- |
| Mobile framework | React Native CLI 0.77.3 ไม่ใช้ Expo |
| UI library | React 18.3.1 |
| ภาษา | TypeScript 5.0.4 |
| Navigation | Internal tab shell และ state ภายในแอปเดิม |
| รูปแบบหน้าจอ | Theme, component และฟอนต์ Prompt จากแอปเดิม |
| สแกน QR | react-native-vision-camera |
| แสดง QR | qrcode-generator และ component PaymentQrCode ที่มีอยู่ |
| Native platform | Android native project และ iOS native project พร้อม CocoaPods |

หน้าจอต้องรองรับขนาดหน้าจอที่แตกต่างกัน รวมถึงมือถือและแท็บเล็ต การใช้ component หรือ module ร่วมกันระหว่างแอปให้พิจารณาเมื่อเริ่มพัฒนา ยังไม่กำหนดโครงสร้าง repository หรือ shared package ในขั้นนี้

## โลโก้และไอคอน

- เพิ่มแถบคาดสีแดงและข้อความ `AUDIT` สีขาว ให้แยกจากแอปผู้ค้าได้ชัดเจน
- ต้องอ่านคำว่า AUDIT ได้เมื่อแสดงเป็นไอคอนขนาดเล็ก
- เตรียมผลลัพธ์สำหรับไอคอน Android, iOS และโลโก้ภายในแอปเมื่อเริ่มงานออกแบบ

ตำแหน่งแถบคาดและรายละเอียดการจัดวางยังไม่ได้กำหนด ส่วนชื่อแสดงในระบบและ package name / bundle identifier ของแอปแยกให้ยืนยันก่อนสร้างโปรเจกต์

## UI และงานออดิทเดิม

ใช้ `src/screens/AuditShell.tsx` และหน้าจอใน `src/screens/audit/` เป็นฐานอ้างอิง โดยคงโครงสร้างหน้าจอและพฤติกรรมหลักดังนี้

1. เข้าสู่ระบบด้วยรหัสเจ้าหน้าที่และรหัสผ่าน
2. แสดงแดชบอร์ดตามวันที่ ได้แก่ งานทั้งหมด รอตรวจ ผิดกฎ และค่าปรับรวม
3. เปิดรายการตรวจ หรือสแกน QR ของรายการจองเพื่อเปิดแบบตรวจ
4. แสดงข้อมูลผู้ค้า บูธ และบริการเสริมที่ใช้อยู่
5. เพิ่มบริการเสริม บันทึกผลไม่ผิดกฎ / ตักเตือน / ผิดกฎ พร้อมหมายเหตุและค่าปรับ
6. สรุปยอดตามการตั้งค่า VAT และบันทึกผลตรวจ
7. แสดงประวัติการตรวจ และป้องกันการบันทึกซ้ำสำหรับรายการที่ตรวจแล้ว

ในหน้าจอเดิม เมื่อบันทึกรายการที่มียอดเรียกเก็บ แอปแสดงข้อความว่าส่งรายการไปยังตะกร้าผู้ค้าแล้ว ส่วนการแสดง QR เพื่อเรียกเก็บเงินทันทีบนแอปเจ้าหน้าที่เป็นความสามารถที่ต้องเพิ่ม

## API ออดิทเดิม

รายการต่อไปนี้เป็น API ที่ service ของแอปเดิมเรียกใช้อยู่ ไม่ใช่ข้อสรุปว่า Backend รองรับความสามารถใหม่ทั้งหมดแล้ว

| งาน | Method | Path | ข้อมูลที่ส่ง |
| --- | --- | --- | --- |
| เข้าสู่ระบบ | POST | `/mobile/audit/auth/login` | Body: `username`, `password` |
| สรุปงาน | GET | `/mobile/audit/summary` | Query: `date` |
| รายการตรวจ | GET | `/mobile/audit/inspections` | Query: `date`, `filter` |
| แบบตรวจ | GET | `/mobile/audit/inspections/{bookingItemId}/form` | Path: `bookingItemId` |
| บันทึกผลตรวจ | POST | `/mobile/audit/inspections/{bookingItemId}/check` | Body: `result`, `note`, `fineAmount`, `accessories` |

`filter` รองรับ `all`, `pending`, `violation`, `fine` ส่วน `accessories` ประกอบด้วย `accessoryId` และ `quantity` ต่อรายการ

หลังเข้าสู่ระบบ service ใช้ `Authorization: Bearer <token>` ข้อมูลผู้ใช้ที่ตอบกลับมีองค์กรและ `marketIds` สำหรับตลาดที่เกี่ยวข้อง การตรวจสิทธิ์ต้องบังคับที่ Backend ด้วย

ผลบันทึกตรวจที่แอปรองรับมี `id`, `result`, `accessoriesAmount`, `fineAmount`, `vatAmount`, `totalAmount` และ `paymentStatus` แต่ยังไม่มีข้อมูล QR ใน response type นี้

การตั้งค่า API ให้ยึด `src/config/environment.ts` ของแอปเดิมและยืนยัน environment อีกครั้งก่อนทดสอบ ไม่ใช้ข้อมูล Production เพื่อทดลองรายการเรียกเก็บเงิน

## การสร้าง QR เรียกเก็บเงินทันที

Flow ตั้งต้นสำหรับงานออดิทที่มีรายการจอง:

1. เจ้าหน้าที่บันทึกผลตรวจและรายการเรียกเก็บ
2. แสดงสรุปยอดจาก Backend
3. สร้างหรือเรียกคืน QR ของรายการเรียกเก็บนั้นให้ผู้ค้าสแกนจ่าย
4. แสดงสถานะรอชำระ และติดตามผลจาก Backend
5. แสดงชำระสำเร็จเมื่อ Backend ยืนยัน พร้อมเลขอ้างอิงรายการ

ต้องป้องกันการสร้างรายการและรับชำระซ้ำเมื่อกดซ้ำ เครือข่ายขาด หรือกลับเข้าหน้ารายการเดิม การแสดง QR หรือการที่ผู้ค้าสแกนแล้วเพียงอย่างเดียวไม่ถือว่าชำระสำเร็จ

แอปเดิมมีส่วนแสดง QR และ flow ชำระเงินของผู้ค้า แต่ต้องตรวจสอบสิทธิ์และสัญญาข้อมูลสำหรับเจ้าหน้าที่ก่อนนำมาใช้ ไม่ถือว่า token เจ้าหน้าที่ใช้แทน session ชำระเงินของผู้ค้าได้ทันที

## ตลาดที่ตั้งค่าเก็บเงินเอง

เมื่อเลือกตลาดที่ตั้งค่า “เก็บเงินเอง” ต้องใช้หน้าเก็บเงินแบบ POS โดยไม่บังคับมีบูธหรือการจอง และไม่สร้างบูธหรือรายการจองจำลองเพื่อให้เรียกเก็บเงินได้

Flow ตั้งต้นสำหรับออกแบบรายละเอียดต่อ:

1. เลือกตลาดที่เจ้าหน้าที่มีสิทธิ์และเปิดโหมดเก็บเงินเอง
2. ระบุผู้ค้าหรือข้อมูลอ้างอิงตามรูปแบบที่จะตกลง
3. เพิ่มรายการเรียกเก็บและจำนวน
4. แสดงสรุปยอดและภาษีตามการตั้งค่าที่ Backend ส่งกลับ
5. สร้าง QR เรียกเก็บเงินทันที
6. แสดงสถานะและผลชำระเงินของรายการนั้น

ชนิดรายการ ราคา การระบุผู้ค้า และเงื่อนไขภาษีของ POS ต้องยืนยันก่อนพัฒนา โดยหน้า POS เป็นส่วนเพิ่มเติมจาก UI ออดิทเดิม

## ข้อมูลสำหรับตกลงสัญญา API เพิ่มเติม

ตารางนี้เป็นรายการข้อมูลที่ต้องตกลงกับ Backend ยังไม่กำหนดชื่อ endpoint, field หรือ enum ใหม่ และต้องตรวจ API ที่มีอยู่ก่อนพิจารณาส่วนเพิ่มเติม

| ความสามารถ | ข้อมูลส่งที่ต้องตกลง | ข้อมูลตอบกลับที่ต้องตกลง |
| --- | --- | --- |
| โหลดตลาดสำหรับเจ้าหน้าที่ | ตัวตนและสิทธิ์เจ้าหน้าที่ | ตลาดที่มีสิทธิ์ สถานะเก็บเงินเอง และนโยบายการรับชำระ |
| โหลดรายการสำหรับ POS | ตลาดและบริบทการขาย | รายการที่เรียกเก็บได้ ราคา หน่วย และการตั้งค่าภาษี |
| สร้างรายการเรียกเก็บ | ตลาด ผู้ค้าหรือข้อมูลอ้างอิง รายการและจำนวน หมายเหตุ และกุญแจป้องกันรายการซ้ำ | เลขรายการ ยอดที่ Backend คำนวณ ภาษี และสถานะ |
| สร้างหรือเรียกคืน QR | เลขรายการเรียกเก็บ และกุญแจป้องกันรายการซ้ำ | ข้อมูล QR ยอดชำระ เลขอ้างอิง วันหมดอายุถ้ามี และสถานะ |
| ตรวจสถานะ | เลขรายการหรือเลขอ้างอิง | สถานะล่าสุด ยอดรับชำระ และเวลาชำระเมื่อยืนยันแล้ว |

Backend ต้องตรวจสิทธิ์องค์กร/ตลาดและคำนวณยอดจริง รายการ POS ต้องไม่บังคับมี `bookingItemId` ส่วนรายการจากการตรวจเดิมต้องเชื่อมกับผลตรวจได้เพื่อไม่เรียกเก็บซ้ำกับตะกร้าผู้ค้า

ใช้ token authentication จัดเก็บข้อมูลสำคัญอย่างปลอดภัย และเตรียม log สำหรับ request, response และกิจกรรมตรวจ/เรียกเก็บ/ชำระเงิน โดยปกปิด token รหัสผ่าน และข้อมูลส่วนบุคคลใน log ตามกฎของโปรเจกต์

## ประเด็นที่ต้องยืนยันก่อนเริ่มพัฒนา

- Backend มี API สำหรับตลาดเก็บเงินเองและการเรียกเก็บที่ไม่ผูกการจองแล้วหรือไม่ เพราะ service ออดิทที่แอปใช้อยู่ยังอ้างอิง `bookingItemId`
- QR ใช้ช่องทางใด ใครเป็นผู้รับเงิน และยืนยันการชำระอัตโนมัติหรือต้องตรวจหลักฐาน
- ชนิดรายการและการกำหนดราคาของ POS รวมถึงการระบุผู้ค้าที่ไม่มีบัญชี
- คำว่า “เก็บเงินเอง” ครอบคลุมเงินสดหรือไม่ ขั้นต้นกำหนดเฉพาะการสร้าง QR ยังไม่เพิ่มการรับเงินสดเป็นขอบเขตที่ตกลงแล้ว
- สิทธิ์ยกเลิกรายการ เปลี่ยนยอด และเงื่อนไข QR หมดอายุ รวมถึงผลต่อรายการในตะกร้าผู้ค้าเดิม
- ชื่อแอป package name / bundle identifier และการตั้งค่า native services สำหรับแอปแยก

## เกณฑ์ตรวจรับสำหรับการพัฒนาภายหลัง

- Android และ iOS ใช้ Tech stack เดียวกับแอปผู้ค้า และมีโลโก้/ไอคอนตามข้อกำหนด AUDIT
- งานออดิทเดิมใช้งานได้ครบตาม flow และ API เดิม พร้อมขอบเขตสิทธิ์องค์กรและตลาด
- เจ้าหน้าที่แสดง QR เรียกเก็บจากผลตรวจได้ทันที และเห็นชำระสำเร็จตามผลยืนยันของ Backend
- ตลาดเก็บเงินเองทำรายการผ่านหน้า POS ได้โดยไม่มีบูธหรือการจอง
- กดซ้ำหรือเปิดรายการเดิมไม่สร้างยอดเรียกเก็บซ้ำ และกลับมาตรวจสถานะได้หลังเครือข่ายขาด
- UI ใช้งานได้บนมือถือและแท็บเล็ต โดยมีสถานะกำลังโหลด ข้อผิดพลาด และรอชำระที่ชัดเจน
